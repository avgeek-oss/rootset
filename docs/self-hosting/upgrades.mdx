title: "Releases and upgrades"
description: "Pin all three images to a release version and preserve your installation data."
---

A release publishes `ghcr.io/avgeek-oss/rootset-api:<version>`, `ghcr.io/avgeek-oss/rootset-worker:<version>` and `ghcr.io/avgeek-oss/rootset-web:<version>` for Linux amd64 and arm64. Migrations reuse the API image. All three images share one version and are built from the same reviewed commit.

The release workflow validates the version/tag and requires verification for that exact commit to pass before building images. It assembles the architecture manifests, verifies anonymous access, and tests installation and restart using the pulled images on both native architectures. Only after those checks pass does it publish the GitHub release with image digests and installation files. Publishing a tag does not by itself mean the release is ready for installation.

## Upgrade a released installation

Read the target release notes first. Protect PostgreSQL, object storage, and the persistent application secret/encryption key using your provider's backup tools. Download the target release's Compose file, which pins all images to that version. Preserve your existing `.env` settings, review any configuration changes in the release notes, and pull before replacing running containers.

```bash
docker compose pull
docker compose up -d --wait
docker compose ps
curl --fail http://localhost:4310/health/ready
```

Include `--profile local-db` if you use bundled PostgreSQL. Preserve the Compose project name and volumes. `docker compose down` preserves named volumes; `down --volumes` deletes them.

## Upgrading to v0.1.5

Version `0.1.5` supports in-place upgrades from released `0.1.2`, `0.1.3` and `0.1.4` installations. Back up the database and stop the API and worker before running migrations. Keep your database volume, object storage, application secret and encryption key.

The `0.1.4` release appended the comments schema to the existing baseline. Version `0.1.5` recognizes the exact baseline and migration hashes from `0.1.2` and `0.1.3`, adds the comments schema and deletion log, and reconciles the baseline checksum in one transaction. The original migration ledger, including its timestamps, is retained in `rootset_control.migration_repairs`. Existing rows, users, credentials, metadata and history are preserved. An existing `0.1.4` installation keeps its comments unchanged.

The API and worker images include this compatibility upgrade. Compose's migration service and Towbar's pre-deploy hooks run it through the normal migration command; no manual checksum edit or separate SQL command is needed. Repeating the migration is safe. Unknown hashes, conflicting comment tables and unsupported migration histories still stop the upgrade without resetting data.

For Compose, after downloading the `0.1.5` Compose file and preserving your existing `.env`:

```bash
docker compose pull
docker compose stop api worker web
docker compose run --rm migrate
docker compose up -d --wait
```

For Towbar, stop the existing API and worker before deploying the new images. Deploy the worker first, then the API and UI. The worker's pre-deploy hook migrates the database; its heartbeat is then available for the API readiness check. Image rollback does not reverse database changes. To restore the earlier schema, use the pre-upgrade backup with the matching images and secrets.

## Prelaunch databases

Unreleased prelaunch schemas and unknown modified baselines remain unsupported. Startup refuses them without resetting the original installation. Preserve that database for inspection; do not clear the migration ledger or change its hashes to force startup. The released `0.1.2`–`0.1.4` upgrade path above is separate from these prelaunch schemas.

[Database backups](/backups) protect logical databases through the worker. Rootset has no restore UI or public restore operation yet. Recover the complete installation with PostgreSQL and object-storage tools, with matching secrets and image versions. Do not assume an older application image can read a newer schema.

Row discussions are stored in the shared `rootset_control.row_comments` table. Include the complete control schema and user-data schemas in the same consistent PostgreSQL backup and restore. A CSV/JSON row export does not contain comments, and copying only a logical database's physical tables cannot restore its discussions. Deleting a row, table or database removes its comments from the live installation. Older provider snapshots retain their point-in-time contents according to your backup retention policy.
