Administrators manage a database's backups under **Backup & Restore**. A backup captures every table in that database, including field definitions, records, unique rules, table relations, comments, saved views and retained history.

## Before you begin

Your operator needs to configure a [database backup source](/self-hosting/configuration#database-backup-source) on the worker. If storage is not configured or no backup-enabled worker is online, Rootset shows an empty state instead of the schedule forms.

The backup bucket must exist. Keep the backup encryption key outside Rootset; restoring a package requires its original key.

## Save a schedule

Open **Backup Schedule**, enter the bucket and an optional path prefix, choose a timezone, and enter a cron schedule. For example, `0 2 * * *` runs daily at 02:00 in that timezone.

Choose **Save schedule**. Rootset tests the destination before saving it. If the test fails, the existing schedule stays unchanged. Leading and trailing slashes in the prefix are removed automatically.

The schedule belongs to the database and continues if its configuring administrator leaves. Choose **Delete schedule** to stop scheduled backups; this does not delete completed packages.

Use **Retention and alerts** to choose how many successful backups to keep and how long a scheduled backup can be overdue before notifying administrators. Leave the backup count empty to keep all managed backups. The most recent successful backup and packages needed by restores remain protected.

## Run a backup now

Open **Backup Attempts** and choose **Back up now**. A manual run uses the saved destination. Only one backup for a database can be queued or running at a time.

Backup Attempts lists manual and scheduled runs, destination tests and failures. Successful backups show the snapshot time, size, table and row counts, and storage path. Queued or running work is not a completed backup. Use **Cancel** when you need to stop a pending attempt.

## Restore a database

Choose **Restore** on a successful backup, then **Verify backup**. Rootset reads and verifies the package before offering the restore. Review its tables, counts and compatibility result, choose a name, and confirm the restore.

A restore creates a new database; it does not replace the source database. Open **Restore Attempts** to follow its progress. Once it succeeds, open the restored database and verify the records before using it.

The restore needs a worker with access to the original backup source and encryption key. If a database was deleted, the managed backup can still be recoverable through the [restore API](/api-reference/previewDatabaseRestore) when you have the backup reference and required administrator access.

## What a database backup contains

Backups preserve typed values, NULLs, identifiers, counters, comments and retained history. Image and URL fields retain their URLs; their remote files are not downloaded.

Accounts, sessions, API keys, OAuth grants, queued jobs and installation credentials are outside a database backup. For recovery of the whole installation, follow [Backup and recovery](/self-hosting/backup).
