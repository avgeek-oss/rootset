Right-click a cell and select **View cell history**. The modal displays changes in a paginated table, including the previous value, new value and time of change. Dates and times use your display preferences.

Rootset automatically keeps the latest **200 saved changes per cell**. There is no retention policy, archive schedule or history backup setting to configure. A failed edit does not become a saved change.

History exists only while its cell exists. Deleting a row, field, table or database removes the corresponding cell history. Administrators do not retain a separate deleted-data changelog.

## Activity

Open **Operate → Activity** for a chronological table of retained record changes, schema changes, imports, exports, backups and restores. A database or table also has **Data → Activity**, scoped to that resource.

Search by activity, actor name or ID, database or table name, or import filename. Filter by type and time window. Dates follow your account preferences. Each page uses the same time cutoff; select **Refresh** to include newer events. A record link opens its full-record drawer. Request links open the corresponding import, export or backup history. Deleted resources keep their schema and request metadata but have no live link. Tables in maintenance show their status without a live link.

Activity follows current permissions. Record changes require row and history read access. Background requests follow the same purpose and ownership checks as their request pages; administrators can inspect all requests they are authorised to read. Backup and restore activity is available only to administrators with the required backup access. Personal saved views and raw cell values, job payloads, provider errors and credentials do not appear in activity search.

Record activity is a summary of retained cell history, grouped by mutation. It follows the same 200-change limit and deletion behaviour described above; it is not a permanent record-deletion log. Imports appear as validation and import requests rather than one event per imported record. Job requests and terminal outcomes are retained separately, so a failed attempt remains visible after a retry. Successful schema changes and restores use their committed resource history to avoid duplicate completion events. Restored record and schema history keeps its original timestamps; operational job queues and their activity are not restored from the package.
