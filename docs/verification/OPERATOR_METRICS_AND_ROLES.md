# Operator metrics and runtime roles

Rootset emits one bounded structured observation for each completed HTTP request. The API adapter supplies the generated request ID, catalog operation ID or fixed protocol label, response status, duration and typed error code. The observer accepts only those fields. It excludes URLs, query strings, headers, bodies, values, credentials and raw exception messages. A failed log sink leaves the completed response intact and increments a visible logging failure counter.

The installation operator status includes process counters, fixed duration buckets and actual occupancy of each configured named PostgreSQL pool. Request counters cover the current process lifetime; they reset at restart, and the response records that scope explicitly. Labels have bounded lengths and at most 256 operation buckets. The API and worker instances require their own log collection and process observations; process counters are not represented as a complete installation-wide request total.

A fixed aggregate-only PostgreSQL function supplies installation observations across organisations. It reports connection and transaction pressure, temporary files/bytes, WAL directory/generated bytes, queue age and expired leases, verified backup age and notification failures, email delivery retries, schema/index state, worker freshness, native data/index bytes, retained history counts/bytes and artifact bytes. These counters identify pressure without returning row values, credentials or SQL text. Its explicit `row_security=off` setting fails if the restricted definer loses its required authority. If the database query or schema validation fails, the observer reports metrics as unavailable with a null database payload; it never fills inaccessible organisations with zero counts.

Operator signals use fixed messages for connection/pool pressure, long idle transactions, old queue work, expired leases, missing/degraded workers, email failures/retries, failed schema jobs, invalid indexes, failed backups/notifications and missing recovery points. The installation status separately reports tested PostgreSQL, object-storage and SMTP dependencies and storage admission configuration. Disk headroom comes from the PostgreSQL-host capacity reporter and its bounded freshness rules. WAL and temporary-byte fields are measured observations; a static byte value alone is not classified as impending disk exhaustion.

Migration 027 removes the runtime DDL login's membership in the deployment superuser role. Managed native schemas/tables and storage functions belong to a no-login, non-superuser, non-bypass owner. Fixed identity lookups, worker directories, capacity accounting and operator metrics use separate no-login definer owners with narrowly granted table columns and privileges. Runtime login roles cannot become these protected owners. Migrations serialize shared role catalog changes across concurrent databases; per-database migration advisory locks alone cannot coordinate cluster-global roles.

The DDL login is a **trusted schema service credential**. It can assume the managed storage owner and alter owned native objects, including their RLS policies and triggers. `NOBYPASSRLS` does not make an adversarial table owner unable to disable RLS. Ordinary application actors use the application role and cannot do this. Protection against hostile use of the DDL SQL credential would require a different design with narrowly callable schema functions and no table-owner membership. DB-05 evidence must retain this trust boundary explicitly; role attributes and ordinary peer-RLS tests do not establish that stronger property.

The separate-cluster ownership suite reproduces the original DDL-to-superuser escalation, upgrades retained deleted-object metadata alongside real physical rows and history partitions, and applies forward migrations concurrently in two databases. It checks actual denials for protected/system roles, superuser role creation, server program execution, protected function/table alteration, privileged trigger installation and credential reads through a native view. Managed row/history writes and normal peer RLS continue to work after the upgrade.

The operator integration cases call the real aggregate function through the identity runtime role and verify counts across multiple organisations. They exercise actual connection saturation and SMTP socket failure, then inspect retry state, expired persisted leases, old queued jobs, degraded/stale worker records and failed schema journals. These explicit QA states prove signal behavior; they do not replace complete scheduler, job recovery, dependency recovery or hardware acceptance runs. Logger tests separately check secret exclusion, label cardinality, unknown database metrics and log-sink failure. Every report remains development evidence until the immutable candidate and full gate requirements have been reviewed.
