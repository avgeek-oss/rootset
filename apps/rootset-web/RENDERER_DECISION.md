# Spreadsheet renderer

Rootset uses an accessible DOM grid with two independent bounds: a 200-row server window and a virtual viewport inside that window. The main grid never creates a DOM spacer for five million rows. First, middle, last, and explicit row-position navigation use the server query session and anchor adapter. The footer reports the logical range separately from the local scroll position.

Glide 6.0.3 was evaluated as the architecture candidate. Its published peer dependency supports React 16–18, while the chosen public HeroUI 3 and Next.js 16 stack uses React 19. Rootset does not force that unsupported combination. The DOM renderer preserves cell editing, type validation, history, selection and copy/paste rather than providing a reduced alternative view.

Visible rows have four rows of overscan. Visible columns have 100 px of overscan; frozen columns remain mounted. Horizontal navigation fetches the projected columns for the existing logical row position. Offscreen values are absent from the result instead of being rendered and formatted eagerly. JSON editing is lazy. A viewport keeps a maximum of five server windows, with a 32 MiB encoded-value budget, and clears them when schema, authority, or query identity changes. TanStack Query stores table/schema metadata separately.

The grid uses `grid`, `row`, `columnheader`, `rowheader`, and `gridcell` semantics, logical `aria-rowindex`, total cardinality when known, `aria-activedescendant`, and a polite focus announcement. Arrow keys, Home/End, Tab, Shift selection, Enter/F2, direct typing, and Escape have explicit behavior. Native modal dialogs trap editor focus and restore the opener. Cell drafts stay local until a mutation returns a committed revision. A conflict keeps the draft and requires explicit review before retrying against the current revision.

Clipboard parsing preserves quoted multiline text, tabs, quotes, Unicode and JSON. Paste has a visible preview and uses the shared atomic mutation schema. Pasting beyond the current window or the atomic limit opens the import workflow; it does not claim the larger paste was committed.

Unit tests verify window eviction/byte limits, viewport bounds, lossless TSV, cell validation and timezone conversion. The production standalone build, TypeScript, lint and all 56 web unit/render tests pass. Actual Chromium and WebKit runs use the live Next application and PostgreSQL fixtures, including the five-million-row, 24-column table and a separate 200-column table. The WebKit route review passes light/dark, keyboard editor focus and return, 390 × 844 touch editing, first/middle/last logical windows, and all 20 settings sections without reported JavaScript, endpoint or axe errors. The 200% zoom check uses document CSS zoom; native browser zoom and assistive-technology review remain separate acceptance evidence.

The development Chromium five-minute continuous-scroll run measured a 1,163 ms first usable viewport, 59.9 median FPS, 16.8 ms p95 frame time, zero one-second freezes, and approximately 55.5 MiB net browser-process RSS growth without forced garbage collection. DOM and cache bounds held throughout. This is development evidence, not acceptance for the capped installation profile. Final capped Chromium/WebKit timings are recorded separately by the release verification ledger.

Account settings use the published Avgeek design-system patterns and Towbar's navigation and fixed copy. Passkeys provide the second sign-in step and fresh session-bound proof; authenticator/TOTP enrollment and code verification are removed. Real PostgreSQL identity tests use signed virtual WebAuthn registration/assertion responses to check user verification, origin, replay, pending sign-in/session binding, password gates and atomic passkey recovery-code consumption. Browser QA uses separate synthetic installations and retains no secrets in committed evidence. Local rendered checks and automated security tests have distinct evidence boundaries; neither alone establishes full-scale product acceptance.

Browser requests now go directly to the configured public API origin. The API applies the ordinary 8 MiB JSON limit and the separate 128 MiB streamed upload limit, while the Next service serves the UI shell independently. Earlier rendered-browser evidence predates this split-origin transport and needs a new run against the final candidate.
