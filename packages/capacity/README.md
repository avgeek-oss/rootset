# PostgreSQL storage admission

Rootset stores capacity policy in PostgreSQL. Unconfigured limits are `null`; usage is always measured. The installation quota uses `pg_database_size`, including live tables, indexes, TOAST, history and account/control data. The organisation quota uses the complete physical allocation of its Rootset database schemas plus transactionally measured JSONB row-value bytes in shared MDM control/history relations (`pg_column_size(to_jsonb(row))`). This retained-control charge is stable across PostgreSQL TOAST compression and updates. Shared control indexes, catalog overhead, database WAL and temporary files belong to installation/disk monitoring; they are not presented as exact per-organisation physical usage.

Every configured MDM growth transaction reserves a conservative byte budget before acquiring table or schema locks. Exclusive admission protects the installation across organisations. Both actual usage plus the reservation and the PostgreSQL filesystem's remaining headroom must fit. The native statement guard rejects writes without a reservation. A deferred PostgreSQL constraint trigger repeats the actual allocation check at commit, including callers that omit `finish`; an over-budget operation rolls back its records and history. Retained history and unique registries are charged; tombstoning data does not pretend to reclaim physical storage.

Unconfigured writes and concurrent index builds hold shared policy locks and remain parallel; an operator cannot activate a limit in the middle of an admitted transaction. All transactional lock acquisitions use nonblocking PostgreSQL try-locks. A contending transaction receives `STORAGE_ADMISSION_BUSY` (503) and rolls back, so it cannot hold an old statement snapshot while a concurrent index build waits for snapshots to finish. Session admission polls completed try-lock queries in JavaScript, outside transactions. `STORAGE_POLICY_CHANGED` (503) requests an unchanged retry if policy changes between discovery and locking. Callers should retry with the same idempotency key after the active operation completes.

Quotas govern MDM growth, while account authentication, operator recovery and reads remain available. Approved retention/cleanup can reduce retained tuple charges; PostgreSQL page allocation is only reclaimed by appropriate database maintenance. Operators can increase/disable a limit through the normal bound installation action. No retention runs implicitly to make space.

The minimum-free-space policy requires a fresh report measured **on the PostgreSQL host**, covering data, WAL and all external tablespaces. The reported bytes use filesystem space available to the PostgreSQL OS user. Committed conservative reservation budgets remain charged against a report until the next measurement. A configured minimum with a missing/stale report pauses growth; a `null` minimum does not require a reporter. Existing records remain queryable in either condition.

Create a non-login `rootset_capacity_reporter` group before migration 024. It receives only the storage-path and report functions, with no access to rows, credentials or capacity-policy changes. A dedicated PostgreSQL login may be granted membership in that group. The API and worker logins must not receive reporter membership.

On the PostgreSQL host, call `reportPostgresFilesystem(pool)` from `@rootset/capacity/reporter` with that dedicated connection. It validates the local `PG_VERSION` and postmaster start timestamp against the connected server before measuring its paths using `statfs`. A connection to a remote database cannot substitute the API host's filesystem. For the standard PostgreSQL container, `infra/postgres-capacity-health.sh` is the equivalent `psql`/`df` reporter and readiness probe. Mount that script read-only into the PostgreSQL container; do not mount its data volume into an API or worker container.

Run the reporter every five seconds and set `reportMaxAgeSeconds` to at least several reporting intervals. External/managed PostgreSQL needs an equivalent trusted database-host reporter or an integration that measures all actual data/WAL/tablespace volumes. If the provider cannot supply these measurements, leave the minimum free-space policy `null` and rely on the provider's disk alarms; the UI truthfully reports unavailable filesystem values.

An operation reservation is an admission budget, not a filesystem hard limit. WAL, concurrent non-MDM account activity, autovacuum, temporary files, failed-transaction pages and other databases on a shared volume can consume space between reports. Configure an operational minimum large enough for those activities; maintain PostgreSQL/provider disk alarms and connection/temp-file limits. The report age, reserved headroom, measured usage and specific refusal reason are operator signals. Rootset does not claim that a small row-byte quota alone can protect an arbitrary database host from every source of disk exhaustion.
